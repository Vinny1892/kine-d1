# MT-1, MT-2, MT-4, MT-5 — Parity, conformance, load and chaos

**Status:** ✅ done · **Date:** 2026-09-07

## MT-1 — Parity with the reference backend

The baseline is not the SQLite driver: its tests only cover `VACUUM`. It is
`pkg/drivers/memory`, with 22 cases — the other backend implementing
`server.Backend` directly.

The 9 missing cases were ported into `pkg/drivers/mongo/parity_test.go`. One
adaptation was needed: in `memory` the revisions are dense (1, 2, 3) and the
tests compare against literals; here they come from `clusterTime` and jump, so
comparisons are against the returned revision.

### A parity bug found

**`toKV()` was not populating `Version`.** `server.KeyValue` has that field, and
etcd uses it to count modifications since creation: 1 on create, 2 on the first
update, resetting to 1 when a key is recreated after deletion. `memory`
maintains it; mongo returned zero for everything.

Fixed with a `version` field in the document, incremented in
`Create`/`Update`/`Delete`, and the watch's `PrevKV` now exposes the previous
version.

This is exactly the kind of silent divergence a parity test exists to catch:
nothing broke, and the apiserver simply received a wrong metadata field.

## MT-2 — etcd conformance over the protocol

`test/mongo/conformance_test.go` exercises the patterns the apiserver actually
emits:

| Case | Result |
|---|---|
| Lease with TTL (Grant + Put + expiry) | ✅ |
| Range: prefix, limit, `CountOnly`, `KeysOnly` | ✅ |
| Conditional delete Txn (right and wrong revision) | ✅ |
| Watch with `WithPrevKV` and `WithRev` | ✅ |
| Compact + `ErrCompacted` when reading an old revision | ✅ |

### What the first failing test taught

The conditional delete failed with `unsupported operations in txn request`.
**The test was wrong, not the driver.** kine recognises `Txn` patterns by
**exact form** (`pkg/server/limited.go:29`): a conditional delete requires an
`Else` branch containing a `Range` (`pkg/server/delete.go:19`). I had omitted
the `Else`; the apiserver always sends it.

Worth recording, because it is a trap for anyone writing tests against kine:
`Txn` is not generic, it is a closed set of recognised shapes.

## MT-4 — Load through the full stack

[MSPIKE-6](mspike-6.md) measured the MongoDB driver directly. Here the
measurement crosses **gRPC → kine → MongoDB**, the path the apiserver takes.

300 objects of 3 KB, concurrency 12:

```
300 writes in 14.8s = 20.3 ops/s   (0 errors)
latency p50=884ms  p95=989ms  p99=1,119ms

LIST of 300 keys (0.9 MB) .... 191ms
LIST keys-only ............... 55ms
```

**The number that matters is the p50 of 884 ms.** The isolated driver inserts
in 26 ms; through the full stack, at concurrency 12, the apiserver feels
884 ms. Two sources: each kine `Put` costs ~3 round trips to MongoDB (the
current-state `find`, the insert, and the revision update), and 12 concurrent
writes contend for the same single-threaded primary.

The p99 of 1.1 s sits comfortably below leader election's 10 s `RenewDeadline` —
the test fails explicitly if it goes past that.

`keys-only` being **3.5× faster** confirms through the full stack what MSPIKE-5
measured in the driver: the LIST bottleneck is payload, not indexes.

## MT-5 — Chaos

### The watch survives interruption without losing revisions

A watch is cancelled mid-stream, four writes happen with no watch active, and a
second watch resumes from the last revision seen:

```
watch 1 cancelled after seeing revision 22568011563010
watch 2 recovered all 4 writes from the gap
```

No event lost, none out of order. This is the pattern the apiserver uses when
reconnecting.

### Writes do not suffer from heavy reads

188 complete LISTs in parallel (4 goroutines) while 30 writes happen:

```
0 errors
write latency: p50=87ms  p99=673ms
```

Notably **better** than the load test (884 ms), which pinpoints the bottleneck:
it is **concurrent writing**, not reading. Heavy reads barely disturb writes —
the opposite of what one would expect from a single-threaded database, and
explainable because reads hit the same primary but do not contend for write
locks.

## Consequence for usage guidance

The practical ceiling already recorded (~30 mutations/s) still holds, but now
with the latency the apiserver actually feels:

| Write concurrency | p50 seen by the apiserver |
|---|---|
| 1 (sequential) | ~87 ms |
| 12 | ~884 ms |

In other words: **what hurts is not volume, it is concurrency.** A cluster with
few simultaneous writers copes well; one with many controllers writing at once
feels the queue.
